2.2 Functional Requirements
1. The app must let a user add, edit, archive, and remove a medication record.
2. Each medication must support name, strength/dosage, instructions, and one or more scheduled times.
3. The Today view must sort scheduled doses by time and show a clear status for each dose.
4. The app must create local reminders that do not require an active internet connection.
5. Reminder content must include the medication name, strength/dosage, and relevant instructions entered by the user.
6. A user must be able to record a scheduled dose as Taken or Skipped. Overdue doses may be displayed as Missed based on the configured rule.
7. After a dose-status change, the app must provide immediate Undo and allow the record to be corrected later from history.
8. Medication details, schedule, reminders, dose logging, symptom entry, and recent history must remain available offline.
9. Changes made offline must be queued and synchronized when connectivity returns without blocking local use.
10. Users must be able to record symptoms or side effects with severity, date/time, and optional notes.
11. Users must be able to record refill information for medication and configure a low-supply reminder.
12. The app must generate an appointment summary for a selected date range.
13. The appointment summary should include medication list, dose history/adherence, symptoms or side effects, allergies, refill information, and recent medication changes when those fields are available.
14. Users must be able to enable or disable spoken medication reminders.
15. Visual reminder information must remain available when voice reminders are disabled or unavailable.
16. Caregiver access must require user approval and must be limited to the permissions granted by the user.
17. A caregiver must not be able to change medication schedules unless the user has explicitly granted that permission.
18. The app must warn the user when notification permission is disabled or when reminders cannot be scheduled.
19. Before exporting or sharing health information, the app must show what information will be shared and require confirmation.
20. If calendar integration is implemented, it must be opt-in and must request only the permissions needed for that feature.

4.3 Data Flow and Offline State
The user performs an action, such as marking a dose Taken.
The app validates the action and writes it to local storage first.
The interface updates immediately, the user does not wait for the network.
If the device is offline, the change is marked Sync.
When connectivity returns, the sync service sends queued changes to the REST API.
The server stores the update and the local record is marked Synced.
If a conflict is detected, the app preserves the local record and flags the item for review instead of silently overwriting it.

Section 5: Requirements Refinement Meeting Documentation
5.1 Meeting Details

5.2 Mock-User Feedback Considered
The most consistent feedback was not about adding more screens. It was about making the core medication workflow more forgiving. Users wanted reminders that identify exactly what is due, visible Taken/Missed status, a way to correct accidental taps, useful offline behavior, larger and more readable controls, high contrast, optional voice support, appointment-ready summaries, refill information, and caregiver access that does not remove control from the medication user.

5.3 Decisions Made
1. Medication reminders will include strength/dosage and relevant instructions instead of a generic “time to take medication” message.
2. Dose status will remain reversible: users get immediate Undo and can correct an entry later from history.
3. Offline access is a core behavior, not a fallback. Reminders, schedule, essential medication information, dose logging, and symptom entry must continue without a connection.
4. Appointment summaries will include symptoms/side effects, allergies, refill information, and recent medication changes where those fields are available.
5. Caregiver access will be user-controlled. Schedule changes are not allowed unless the medication user explicitly grants that permission.
6. Accessibility checks will be attached to the stories they affect, so large text, contrast, keyboard access, screen-reader support, and touch-target sizing are verified during development.

Priority | Rationale
Must-Have | These features are necessary to safely complete the core medication workflow: accurate medication data, today’s schedule, specific reminders, dose status, reversible corrections, offline operation, and accessible controls. If these are not reliable, the product does not meet its primary purpose.
Should-Have | Symptoms/side effects, appointment summaries, voice reminders, and refill information add substantial value but the user can still complete the minimum medication-management workflow without them.
Nice-to-Have | Caregiver sharing and calendar integration introduce additional permissions, external integrations, and synchronization work. They are useful but should not delay the stable medication and accessibility experience.
Risk | Why it matters | Mitigation
Offline synchronization | Local and server copies can disagree after the device reconnects. | Write locally first, track sync status, use updated timestamps, test reconnect scenarios early, and flag unresolved conflicts instead of silently overwriting them.
Notification reliability | Medication reminders are a central workflow; disabled permissions or OS behavior can prevent delivery. | Use local notifications, verify permission state, show a clear warning when reminders cannot be scheduled, and test on each supported mobile platform.
Cross-platform differences | Notifications, local storage, accessibility APIs, and keyboard behavior differ by platform. | Keep shared business logic small, use adapters for platform storage, and run the same acceptance scenarios on every platform.
Large-text layout failures | 200% text can cause clipped labels, overlapping controls, and hidden actions. | Use flexible layouts from the start; test 200% continuously and 250% on primary screens.
Caregiver permission errors | An overly broad permission could expose health information or allow unintended changes. | Default to least privilege; separate view/alert/edit permissions; require user confirmation for schedule-edit access.
Sensitive local data | Offline operation means medication data exists on the device. | Avoid unnecessary fields, protect credentials/tokens with platform secure storage, rely on device security/encryption capabilities, and never log sensitive values in debugging output.
Front-end accessibility complexity | Accessible behavior can regress as components change. | Create shared accessible button/input components and include accessibility checks in code review and definition of done.
Team risk | Mitigation
Front-end learning curve | Start with a small vertical slice: Today screen → reminder → Taken/Skipped. Pair on the first reusable components and document the pattern before building more screens.
Accessibility implementation is unfamiliar | Use a short accessibility checklist in every pull request, keep reusable controls accessible by default, and use automated tools as an early warning rather than the only test.
Knowledge becomes concentrated in one teammate | Follow the charter’s rotating roles, review each other’s pull requests, and use short pairing sessions for difficult tasks.
Integration ownership is unclear | Keep work in small branches, assign one owner per story, and require at least one teammate review before merge.
Schedule risk | Contingency
Offline sync takes longer than expected | Finish local-only medication and dose workflows first. A reliable offline experience is more important than sophisticated multi-device synchronization for the initial milestone.
Cross-platform bugs consume too much time | Complete one end-to-end workflow on all platforms before expanding secondary features. Fix architecture differences early.
Accessibility issues are discovered late | Run large-text, keyboard, and screen-reader checks as each screen is built. Do not defer them to final QA.
Caregiver or calendar integration expands scope | Keep these Nice-to-Have. If the schedule slips, preserve the permission model in the design but defer the external integration.
A team member becomes unavailable | Keep work visible in Git, maintain current setup notes, use small PRs, and rebalance work in the weekly meeting as described in the team charter.
Testing accumulates near the deadline | Attach tests to acceptance criteria and require critical-path tests before merge rather than creating a separate testing phase at the end.
